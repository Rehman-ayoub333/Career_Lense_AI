# Architectural Decision Register

Format: Decision / Context / Alternatives considered / Rationale / Status. Only decisions with genuine alternatives are listed — restating an unchanged existing mechanism is not a "decision" for this register unless an alternative was seriously weighed.

## ADR-01: Not agentic
**Decision:** CareerLens is not described or built as an agentic system. **Context:** turn-2 audit explicitly required an honest agentic-AI determination. **Alternatives considered:** adding autonomous multi-step planning/tool selection to justify "agentic" marketing language; adding a memory/session-continuity layer. **Rationale:** JAIR survey's definition (reason+act+interact+autonomy) does not match the actual single-shot, stateless, no-tool-use, no-memory pipeline confirmed by direct source reads; claiming otherwise would be an unfalsifiable, unverifiable marketing claim in a thesis context, where honesty is scored. **Status:** Final, binding across all documents.

## ADR-02: No RAG
**Decision:** the evidence mechanism is not called or built as RAG. **Context:** "evidence retrieval" language in early planning risked implying an external-corpus retrieval system. **Alternatives considered:** building an actual external knowledge base (e.g. an ESCO skill ontology lookup) to justify RAG framing. **Rationale:** CV and JD are already fully in the prompt context; there is no external corpus to retrieve from — the mechanism is span-location within already-present text, a distinct and honestly-labeled thing. **Status:** Final.

## ADR-03: Deterministic (non-LLM) evidence verification, single default path
**Decision:** Stage 2 verification is pure string-matching code, never a second LLM call in the default path. **Context:** the entire research contribution's falsifiability depends on this split. **Alternatives considered:** LLM-as-judge for verification (simpler to build, faster to prototype); embedding-similarity verification (smarter, but non-deterministic and harder to explain/defend in a viva). **Rationale:** if the LLM verifies its own claims, RQ1 becomes circular and unfalsifiable — a second model call correlated with the first model's errors would inflate the faithfulness metric without proving anything. **Status:** Final, the single most load-bearing decision in the entire plan.

## ADR-04: Stage 2b LLM adjudication is SHOULD-HAVE, not MUST-HAVE, and never independently declares `verified`
**Decision:** an optional escalation step may narrow `uncertain` claims toward `verified`/`unresolved`, but only as a secondary, clearly-scoped, off-by-default enhancement. **Context:** pure string-matching alone will misclassify genuine paraphrase as `uncertain` more often than a human would. **Alternatives considered:** shipping without any adjudication step at all (simpler, but leaves a known accuracy gap); making adjudication a MUST-HAVE (adds LLM-call cost/latency/non-determinism to the critical path for a thesis-scope project). **Rationale:** ships the falsifiable core first; adjudication is a documented, bounded enhancement that cannot regress the core mechanism's falsifiability since it never grants `verified` status the deterministic check itself didn't support. **Status:** Final as SHOULD-HAVE.

## ADR-05: Single held-out split, not k-fold
**Decision:** 70/30 fixed split for threshold calibration/final evaluation. **Context:** dataset target size is 60–150 items. **Alternatives considered:** k-fold cross-validation (more standard for larger datasets). **Rationale:** k-fold on a 60–150-item set with per-fold threshold recalibration would be reaching for statistical machinery the sample size can't actually support meaningfully, and would complicate the leakage-prevention story (perturbation variants staying with their base item) for no real benefit at this scale. **Status:** Final.

## ADR-06: `--unresolved` as a new, distinct calm-slate token, not a repurposed existing one
**Decision:** new `--unresolved`/`--unresolved-text` tokens (hsl 220 18% 46% / #606E8A and hsl 220 20% 66% / #97A3BA), not reuse of the existing neutral/gray token. **Context:** `Tag variant="missing"` currently renders red for absent evidence, violating the "red = system error only" doctrine. **Alternatives considered:** reusing the existing neutral gray token (simpler, fewer new tokens); using amber for unresolved (blurs the distinct meaning of `uncertain`). **Rationale:** unresolved needs to read as "genuinely distinct from both a positive and a negative signal," not as an afterthought reuse of a token designed for other purposes — a dedicated token also makes the doctrine violation structurally harder to accidentally reintroduce, since removing `variant="missing"`'s red mapping is a visible, intentional change, not an ambiguous reuse. **Status:** Final.

## ADR-07: Marked-document view replaces the 8-tab dashboard as the default results experience
**Decision:** evidence-in-context is the primary view; Rewrite/Cover Letter/Interview Prep/Chat move to a secondary "Tools" strip. **Context:** turn-3 master plan's "evidence as hero" requirement. **Alternatives considered:** keeping all 8 tabs at equal visual weight (current state); a single long-scroll page with no tabs at all (loses the useful separation between evidentiary and generated content). **Rationale:** evidentiary content (what the system found and verified) and generated content (rewrites, letters) are epistemically different — conflating them at equal visual weight implies equal certainty, which is false. **Status:** Final.

## ADR-08: research/ as a sibling directory, not a subpackage of careerlens/
**Decision:** `research/` never imports from `careerlens/`'s internals except the one explicit exception (`grounding.ts` direct import for the ablation study). **Context:** turn-4 brief explicitly required this separation. **Alternatives considered:** a monorepo-package structure with research/ formally depending on a published careerlens internal package (more "correct" engineering, disproportionate for a thesis-scope project); research/ calling only the public HTTP API with no exception (cleaner boundary, but makes the ablation study's Stage-2-removal condition impossible to isolate precisely without standing up multiple server configurations). **Rationale:** the one named exception is narrow, justified, and documented — not a general loophole. **Status:** Final.

## ADR-09: Single model, no fallback provider, for this thesis's scope
**Decision:** `gemini-2.5-flash` only; the existing provider-registry seam is not used to add a second provider in this plan. **Context:** multi-provider evaluation would strengthen generalizability claims. **Alternatives considered:** adding a second provider (OpenAI/Anthropic) for cross-model comparison. **Rationale:** out of scope/budget for a BS FYP timeline; stated as an honest limitation (`RESEARCH_CONTRIBUTION_FINAL.md`) rather than either quietly skipped or falsely implied as done. **Status:** Final for this plan; explicitly flagged as future work.

## ADR-10: `evidence_quote` null → empty-string sentinel, not a widened provider contract
**Decision:** Stage 1's `evidence_quote` is emitted as `""` when absent, coerced to `null` by `normalizeAnalysisDraft` immediately after parsing — `grounding.ts` and every downstream consumer only ever sees `string | null`, never the sentinel. **Context:** `DATA_CONTRACTS_FINAL.md` specifies `evidence_quote: string | null`; `OPEN_QUESTIONS_FINAL.md` suggested attempting direct nullable typing first. **Alternatives considered:** widening `JsonSchema` in `lib/ai/types.ts` and `lib/ai/google.ts`'s request builder to express a true nullable variant (more "correct," but touches the shared provider contract other prompts also use, for a Phase 1 type-only pass). **Rationale:** `JsonSchema`'s variants each carry one concrete type with no nullable flag today; adding one is a provider-layer change with blast radius beyond this one field, and the sentinel-plus-immediate-coercion approach was already the documented fallback. **Status:** Final for this implementation; revisit only if a second field needs the same treatment and the provider-layer change starts paying for itself.

## ADR-11: Stage-1 draft types (`AnalysisDraft`/`ClaimDraft`/`ATSCheckDraft`) as a new, separate type family from `AnalysisResult`
**Decision:** the model's raw output is typed as its own family, distinct from the canonical `AnalysisResult`/`RequirementClaim`/`VerifiedClaim`/`ATSCheck` types in `DATA_CONTRACTS_FINAL.md`. **Context:** not explicit in `DATA_CONTRACTS_FINAL.md`, added during Phase 1 implementation. **Alternatives considered:** having Stage 1 populate a partial/optional-fields version of the canonical types directly (fewer type names, but makes it a runtime discipline, not a compile error, to accidentally pass unverified model output off as verified). **Rationale:** the model's output genuinely cannot be an `AnalysisResult` — it must not be able to produce `id`, `verification`, `match_score`, `hallucination_candidate`, `coverage`, or `ATSCheck.source`, since those are exactly the fields Stage 2/3 compute. A separate draft type makes it a compile error to skip verification, which is stronger than a runtime convention. **Status:** Final, accepted as a legitimate implementation-level extension of `DATA_CONTRACTS_FINAL.md` that reinforces ADR-03 rather than bending it.

## ADR-12: `scholarship_specific_tips` removed
**Decision:** the field is dropped from `AnalysisResult` entirely. **Context:** a genuine conflict was found between `DATA_CONTRACTS_FINAL.md` (canonical, omits it) and `PROMPT_ARCHITECTURE_FINAL.md` (said "unchanged," now corrected). **Alternatives considered:** restoring it as an optional field to preserve the scholarship-mode feature. **Rationale:** `DATA_CONTRACTS_FINAL.md` is the stated single source of truth for types/shapes; Master Plan §11.1 independently agrees it's omitted; `PROMPT_ARCHITECTURE_FINAL.md`'s line was the stale outlier and has been corrected in place rather than left to cause a second disagreement later. **Status:** Final. If scholarship-specific tips are wanted as a feature later, they should be reintroduced as a deliberate new field with its own ADR, not resurrected from this removed one.

## ADR-13: `ChatTab.tsx` `missingSkills` derived from gap-status claims, chat SHOULD-HAVE not pulled forward
**Decision:** `missingSkills` is computed from `gap`-status claim requirement strings rather than a removed `skills_missing` field; the claims-aware chat context enhancement (`PROMPT_ARCHITECTURE_FINAL.md` Prompt 5 SHOULD-HAVE) stays deferred. **Context:** Phase 1's type cutover broke this call site; `API_CONTRACT_FINAL.md` states the chat request shape is unchanged. **Alternatives considered:** bringing the SHOULD-HAVE chat enhancement forward into Phase 3 to solve this more richly. **Rationale:** the minimal fix preserves the documented wire shape and avoids scope creep into a phase not yet reached; the richer chat context remains available as a documented future enhancement, not lost, just not accelerated without a reason beyond convenience. **Status:** Final for Phase 3.

## ADR-14: Jest retained, Vitest not introduced
**Decision:** keep the existing Jest + ts-jest setup; do not add Vitest. **Context:** `OPEN_QUESTIONS_FINAL.md` originally defaulted to Vitest, on the mistaken premise (traced to a gap in `PROJECT_CURRENT_STATE_AUDIT.md`) that no test runner existed yet. **Alternatives considered:** migrating the 95 existing passing tests to Vitest for the marginally faster iteration/native-ESM story. **Rationale:** a working, passing, already-wired test suite is worth more than a marginal DX improvement at this stage of the project; migrating tests for no functional gain is exactly the kind of unforced churn this plan's discipline exists to avoid. **Status:** Final. Corrects a real gap in the original state audit rather than silently overriding it.

## ADR-15: Git workflow — commit directly to `main` per phase/logical unit, tag phase completions, never squash or rebase before pushing
**Decision:** each phase (and, within a large phase, each clearly separable sub-step) gets its own commit on `main` with a descriptive message referencing the phase/roadmap step, made at the time the work is actually done — not batched into one commit later. After a phase's exit criteria are verified, tag it (e.g. `git tag phase-0-complete`). Push regularly; never use `git commit --amend`, interactive rebase, or squash-merge across multiple days of work before pushing. **Context:** the user wants GitHub's contribution graph, once these commits are pushed, to reflect the actual days work happened — which depends on preserving each commit's original author-date and not collapsing multiple days into one commit. **Alternatives considered:** a branch-per-phase workflow with `--no-ff` merges (marginally cleaner history, more ceremony for a solo FYP repo, and squash-merge — a common default — would collapse a day's several commits into one, working against the graph goal if used carelessly). **Rationale:** direct-to-main commits are simplest to get right consistently across many Claude Code sessions, tags provide the same rollback safety `MIGRATION_PLAN_FINAL.md` wanted from phase gates without branch-management overhead, and the explicit no-squash/no-rebase rule is what actually protects the graph goal. **Status:** Final, binding for every future implementation prompt.

## ADR-16: Token-overlap intersection computed with multiplicity (multiset), not literal deduplicated-set intersection
**Decision:** `grounding.ts`'s `overlapRatio` computes `|intersection(window_tokens, quote_tokens)|` as a multiset (bag) intersection — each token counted per-occurrence, capped by the lesser count on either side — not as literal deduplicated-set intersection, despite `EVIDENCE_VERIFICATION_SPEC.md` §"Deterministic search algorithm" step 3 glossing the formula as "set intersection, not sequence." **Context:** surfaced during Phase 2 implementation. Read completely literally (deduplicated set intersection), the formula contradicts the same spec's own scenario table, which requires "Exact evidence exists → `match_score = 1.0`" unconditionally: any quote containing a repeated token (a repeated stopword like "a"/"the"/"and," or a repeated content word — common in real CV/JD phrasing) would deduplicate in the numerator while `n` in the denominator keeps counting every occurrence, capping the score below 1.0 for a verbatim, unmodified quote. **Alternatives considered:** (a) literal deduplicated set intersection exactly as written — rejected, self-contradicts the spec's own exact-match invariant on any quote with a repeated token, which is not a rare case; (b) multiset/bag intersection with multiplicity — chosen, preserves the order-tolerance the "not sequence" gloss is actually arguing for (a reordered quote should still match) while satisfying exact-match → 1.0 for every quote, including ones with repeated tokens. **Rationale:** the gloss is making a point about order-insensitivity, not literally mandating deduplication — multiset intersection is the only reading consistent with the scenario table's stated invariant. Pinned by a named test in the `grounding.ts` suite so behavior cannot silently drift back to literal set semantics later. **Status:** Final. Exercised per the spec's own stated escape hatch ("deviations belong in `ARCHITECTURAL_DECISION_REGISTER.md`, not silently in code").

## ADR-17: Numeric-token integrity gate added to `grounding.ts`, capping fabricated-number claims at `unresolved`
**Decision:** after the token-overlap score is computed, any pure-digit token present in the normalized quote must also appear as an exact token within the best-matching window. If one or more digit tokens in the quote are absent from that window, the claim's **tier** is capped at `unresolved` — never `verified`, never `uncertain` — regardless of the overall overlap ratio. Two implementation-level sub-decisions, both load-bearing enough to record explicitly rather than leave to the implementer to infer: (1) **"the best-matching window"** means the window produced by the existing scan loop's ordinary argmax, with ties broken by first occurrence in the loop's existing deterministic iteration order (by source position, then by width `n-1`/`n`/`n+1`) — the scan loop itself is not restructured into a two-pass or disqualify-and-rescan design; the gate is applied once, after the existing scan already picked its winner. (2) **`match_score` is left untouched** — the gate overrides tier derivation only; the score keeps its real computed overlap ratio (e.g. `0.93` stays `0.93` even when the tier is gated down to `unresolved`). **Context:** Phase 2 adversarial testing reproduced exactly the case `TESTING_STRATEGY_FINAL.md` names as a "spec-defining bug": CV says "led a team of 4 engineers," the model fabricates "12." Plain token-overlap correctly flags this on a short quote (3/4 tokens overlap → `uncertain`) but wrongly reaches `verified` on a longer, otherwise-accurate quote (13/14 genuine tokens, one fabricated number → 0.93 overlap), because the single fabricated token is diluted below the 0.85 threshold as quote length grows. `OPEN_QUESTIONS_FINAL.md`'s stated trigger for revisiting the matching algorithm ("revisit only if Phase 2's adversarial test suite shows it's insufficient") is met by this finding. **Alternatives considered, for the core gate:** (a) raise the `verified` threshold globally — rejected, does not fix the dilution mechanism, only moves the quote-length at which it recurs, and uniformly degrades legitimate long paraphrases; (b) weight rare/proper-noun tokens above stopwords generally — rejected for this pass, normalization lowercases before tokenizing (per `EVIDENCE_VERIFICATION_SPEC.md` normalization rule 1), destroying the capitalization signal a proper-noun detector needs, so this would require restructuring the normalization pipeline itself, a materially bigger change than the named test case calls for; (c) require contiguous/sequence matching — rejected, directly undoes the deliberate order-tolerance `EVIDENCE_VERIFICATION_SPEC.md` states is intentional, breaking legitimate reordered paraphrase; (d) numeric-token integrity gate, scoped to digit tokens only — chosen, digits survive normalization intact (rule 3 strips only non-letter/non-digit/non-space characters), are cheap to check post-tokenization, and are exactly the highest-value fabrication target in CV claims (team sizes, percentages, dates, dollar amounts). **Alternatives considered, for sub-decision (1):** disqualifying any window that fails the digit check during the scan and letting the next-best surviving window win — rejected, this changes which window (and therefore what score) counts as "the match" for cases far beyond the numeric-fabrication case, is a structural change to the one piece `EVIDENCE_VERIFICATION_SPEC.md` says must be implemented exactly as specified, and buys no benefit the simpler post-hoc gate doesn't already get. **Alternatives considered, for sub-decision (2):** driving `match_score` to `0` on a gate hit — rejected, `match_score` is the number `RESEARCH_EVALUATION_FINAL.md`'s Experiment 1 and evidence-extraction-accuracy metric actually report and the number a future error-analysis pass needs to tell "gate caught a real fabrication" apart from "gate is miscalibrated"; zeroing it would misrepresent genuine token overlap that did exist. **Rationale:** capped at `unresolved` rather than `uncertain` specifically because a fabricated number is the canonical case `RESEARCH_EVALUATION_FINAL.md`'s hallucination-rate metric exists to catch, and per `DATA_CONTRACTS_FINAL.md`, `hallucination_candidate: true` is only ever paired with `verification: 'unresolved'` (never `'uncertain'`) when `evidence_quote` is non-null — capping at `uncertain` would silently exclude this exact fabrication case from the metric it's supposed to feed; `hallucination_candidate` for a gated claim is therefore `true`, computed automatically by `verifyClaims`'s existing `verification === 'unresolved'` rule, with no separate wiring needed. **Known residual gap, logged not silently solved:** this gate does not catch a spelled-out-vs-digit mismatch (CV "four engineers" vs. a quote reading "4 engineers") since token equality is exact post-normalization and number-word normalization was never in scope for this pass. **Status:** Final for Phase 2. Revisit only if the residual spelled-number gap, or an analogous non-numeric fabrication case (e.g. a fabricated proper noun), surfaces in Phase 8/9 real data. **Correction (Phase 3):** the sub-decision (1) parenthetical naming a specific iteration order didn't match your implementation (width outer, position inner) — generalized to "whatever order the implementation already uses." No code change; only the ADR text was wrong.

## ADR-18: `RewriteRequest` wire shape gets one optional `claims` field; corrects `API_CONTRACT_FINAL.md`'s stale "unchanged/invisible on the wire" line for `/api/rewrite`
**Decision:** `POST /api/rewrite`'s request gains a new **optional** field, `claims?: Array<{ requirement: string; category: ClaimCategory; verification: VerificationTier }>` — populated with claims where `verification === 'unresolved' || verification === 'uncertain'` (the mechanical tiers), **not** filtered by the model's self-reported `status === 'gap'`. This resolves the vocabulary mismatch in `PROMPT_ARCHITECTURE_FINAL.md` Prompt 3's "gap/uncertain-tier" phrasing: the field only ever carries `verification`, never `status`, and per `ADR-03`/`CLAIM_MODEL_FINAL.md` the mechanical tier is the one this whole architecture treats as authoritative over the model's own self-report — so "gap/uncertain-tier" is read as informal shorthand for "unresolved-or-uncertain by verification," not as a literal instruction to filter on `status`. When `claims` is present, `getRewritePrompt` prioritizes bullets touching those requirement categories. When absent, falls back to the prior generic "most room to improve" framing — fully functional either way. Prompt builder signature shape (extra parameter vs. an options object) is implementation style, not architecturally significant — match whatever convention the other prompt builders in `lib/prompts.ts` already use. `POST /api/cover-letter`'s request shape is genuinely unchanged — `PROMPT_ARCHITECTURE_FINAL.md` Prompt 4 is explicitly unchanged, so no claims data is needed there; the two endpoints no longer share one blanket answer. **Context:** surfaced during Phase 3 implementation as a real conflict, not invented or guessed past. `BACKEND_ARCHITECTURE_FINAL.md` states the server is stateless with no session storage, so there is no internal source `/api/rewrite` could read `claims` from unless the client sends them — which is definitionally a wire change. `API_CONTRACT_FINAL.md`'s prior line for `/api/rewrite`/`/api/cover-letter` — "internal prompt inputs now include the claims array... this is an internal call-site change, invisible on the wire" — described something that cannot actually be implemented as written. **Alternatives considered:** (a) add an optional `claims` field to `RewriteRequest`, unresolved/uncertain subset only — chosen, additive and backward-compatible, mirrors the non-breaking optional-field pattern `API_CONTRACT_FINAL.md` already uses for chat's `claims` field; (b) reword Prompt 3's instruction generically with no wire change — rejected, quietly under-delivers against a non-SHOULD-HAVE instruction; (c) have `/api/rewrite` internally re-run Stage 1 extraction — rejected, doubles model-call cost to recompute what the client already has. **Rationale:** the client already holds the full `AnalysisResult` in `AnalysisSession` the moment the user reaches the results page — sending the unresolved/uncertain subset back is a minimal wire addition, not a new capability the client lacks; scoped to `requirement`/`category`/`verification` only, keeping payload minimal. **Status:** Final for Phase 3. `API_CONTRACT_FINAL.md` corrected in place (`/api/rewrite` and `/api/cover-letter` documented separately).

## ADR-19: `ats_checks` and `salary_range`/`salary_context` get a live surface in `AssessmentPanel`, not download-only
**Decision:** two new presentational components, `ATSChecklist.tsx` (props `{ checks: ATSCheck[] }`) and `CompensationSummary.tsx` (props `{ salary_range: string, salary_context: string }`), render below `RequirementChecklist` and above the three-action footer inside `AssessmentPanel.tsx`. `ATSChecklist` shows the 8 fixed checks (pass/warn/fail + label + note); `source` ('deterministic'/'model') is shown as a small transparency label, not hidden, per `DATA_CONTRACTS_FINAL.md`'s stated purpose for that field. Neither is added to `ResultsTabs` — ADR-07 already narrowed that strip to exactly Rewrite/Cover Letter/Interview Prep/Chat, and these two are assessment output, not generated content, so they belong beside `CoverageSummary`, not as a 5th tool. **Context:** deleting the old ATS/salary tab content left `ats_checks` and `salary_range`/`salary_context` — still generated every call, still canonical `AnalysisResult` fields — with no on-screen home; they landed only in the downloaded report as a stopgap. Neither `FRONTEND_COMPONENT_ARCHITECTURE.md` nor `FRONTEND_UX_SPEC_FINAL.md` assigned them a destination after the 8-tab rework — a genuine gap, not deliberate. **Alternatives considered:** (a) leave download-only — rejected, discards live-view data core to the product's value prop for no stated reason; (b) a 5th `ResultsTabs` entry — rejected, contradicts ADR-07's "Final" 4-tool narrowing; (c) surface in `AssessmentPanel` — chosen, matches what they actually are. **Status:** Final. `FRONTEND_COMPONENT_ARCHITECTURE.md` is amended to include these two in `AssessmentPanel`'s composition.

## ADR-20: ATS deterministic checks (dates/contact/tables) get a new module, `lib/analysis/ats-checks.ts`, not `grounding.ts`
**Decision:** the three mechanically-checkable `ATSCheck` ids (`dates`, `contact`, `tables`) get real deterministic logic in a new module, `lib/analysis/ats-checks.ts`, invoked in `/api/analyze` after Stage 1 (alongside/before Stage 3 aggregation) and merged into the model's 8-item `ats_checks` output — overriding the model's guess for these 3 ids when conclusive, per `DATA_CONTRACTS_FINAL.md`'s `ATSCheck.source` semantics; `source: 'model'` stays for the other 5 and for any of the 3 that are inconclusive. **Context:** `source` has been hard-coded `'model'` for all 8 since Phase 3 — the deterministic logic never had an owner. An old Master Plan reference said this logic "moves to `grounding.ts`" when the old ATS tab was deleted, but `grounding.ts` per `EVIDENCE_VERIFICATION_SPEC.md` has no ATS responsibility at all — that reference describes something never built and never should live there. **Alternatives considered:** (a) leave `source` permanently `'model'` silently — rejected, quietly drops required, specifically-justified field behavior; (b) fold into `grounding.ts` per the stale reference — rejected, blurs ADR-03's clean claim-evidence-only boundary with an unrelated document-structure check; (c) new small module — chosen, mirrors the Phase 2 `grounding.ts`/`aggregate.ts` split-by-responsibility pattern. **Rationale:** `dates`/`contact`/`tables` are all cheaply, deterministically checkable from `cvText` with plain string/regex logic — same "don't trust the model where code can check" rationale as ADR-03, different field. **Status:** Final. New work, own commit, lands before Phase 7.

## ADR-21: Embedding-similarity baseline uses Gemini's embedding endpoint, not a local model
**Decision:** `research/scripts/baselines/embedding-similarity.ts` computes its secondary baseline via Gemini's embedding endpoint (same `GOOGLE_API_KEY`/provider already configured), not a locally-hosted embedding model. **Context:** `RESEARCH_EVALUATION_FINAL.md` names embedding cosine similarity as a secondary baseline but never specifies the source; the script currently throws rather than guessing. **Alternatives considered:** (a) local embedding model — rejected, new dependency/weights/license surface for a supporting metric; (b) Gemini's embedding endpoint — chosen, no new dependency, reuses the already-configured credential and already-disclosed data flow to Google. **Rationale:** ADR-09 governs the primary pipeline's model-plurality claim for thesis honesty; it doesn't bar a secondary research-only baseline from using a different model class (embeddings, not generation) from the same already-approved vendor. Add one line to `SECURITY_PRIVACY_SPEC.md`'s data-flow description noting research-mode embedding calls reuse the same Gemini credential — no new disclosure category. **Status:** Final for Phase 7/9.

## What this document does not claim
This register lists decisions made during planning, with their reasoning, so a viva examiner or future contributor can see why, not just what. It is not a record of decisions made during implementation — new genuine decisions encountered during coding follow the STOP → REPORT → DO NOT GUESS rule and get added to this register at that time, not guessed and back-filled.
